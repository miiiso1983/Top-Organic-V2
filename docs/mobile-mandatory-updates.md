# Mandatory mobile updates

Build 68 adds an app-wide update gate, installed package build/platform headers, fixed official store links, rechecks on foreground/every two minutes, and an authenticated API 426 gate. The update screen cannot be dismissed by back navigation or a deep link. The last enforced policy is cached across restarts/network loss; a newer installed build or a successful server policy rollback unlocks the UI. A first-ever offline start without policy is not falsely blocked; server operations remain subject to the API gate. HTTP 426 does not log the user out or classify the operation as an offline/network error.

Administration: `/admin/mobile-updates`, protected by `admin.settings` and CSRF on writes. Independent `mobile_update_android` / `mobile_update_ios` JSON settings contain mode (`off`, `pending`, `required`), minimum build, version, verified build, and verification timestamp. `required` does not enforce an unverified target. Recent identified sessions (30 days) are shown with 50-row pagination; hashed bearer tokens are never shown. Change audit label is Arabic. Disabling a policy is an immediate server rollback and reaches active apps on the next policy refresh.

Deploy `database/124_mobile_updates.sql` before the PHP changes. Run `php8.3 bin/check-mobile-release.php` periodically on the server for Android pending policies. This product release gate uses the existing authorized Google service account, obtains an in-memory Android Publisher token, checks the **exact build** in the production release lifecycle for `PUBLISHED`, then checks `completed` full rollout without country targeting in a disposable read edit. It deletes that edit and never commits it. Upload success, an edit marked completed, review pending, approval awaiting publication, staged rollout, and network/API failure do not activate enforcement. A compare-and-swap on the original policy prevents an in-flight check from undoing an administrator's cancellation/change. No iOS setting is changed by this task. Only arm a pending target after its release upload edit has been committed. A pending target must include all existing attendance protection and device compatibility.

Legacy versions <=67 lack the gate UI and version headers. An authenticated push registration identifies the platform **for the same token/session only**; legacy Android then receives an Arabic `app_update_required` message on server operations after Android enforcement activates. New builds always send explicit package metadata and update the session. Native/background clients sharing that token inherit the known metadata. A conflicting platform on one legacy token is marked ambiguous and never guessed from the user's other devices. Unknown/unregistered legacy sessions remain compatible until identified; therefore this is not a complete ban on every old or modified client. It is not hardware attestation and header metadata can be spoofed. To close that gap later requires a staged authenticated device/session migration and/or app attestation; do not globally reject unidentified sessions while iOS is intentionally independent. Existing permissions, face verification, geofence and VPN policies are unchanged.

Verification: PHP policy/session/real Router tests cover outdated/current/future versions, iOS independence, legacy binding, ambiguous sessions, actual rejection before attendance action, no activation during review/staging, and exact-build publication. Flutter widget/API tests cover required screen/back navigation, official store destination, store failure, cached offline gate, rollback, 426 during use, installed headers and no logout/offline queuing classification. Existing mock-location and selfie tests remain green. Real store publication is an external dependency, not implied by these tests.
